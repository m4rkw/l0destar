# ISO-9141 Loopback Test

**Before building, installing or relying on any of this, read the [project disclaimer](../DISCLAIMER.md).**

Verifies the K-line and L-line interface on v2.5K/v2.6K boards using the
L9637D transceiver's bus loopback (TX drives the K-line, same chip's RX
reads it back). No external equipment needed.

On bench setups with two L9637D transceivers, the test instead streams
bytes K1->K2 and K2->K1 across the wire.

## Hardware

- l0destar v2.6K board (L9637D transceiver + TXS0104E level shifter)
- 12V bench supply (powers the K_EN domain via P0.23)
- No external adapter or loopback plug required - the L9637D echoes its
  own transmissions on the shared K-line

## What the test covers

1. **K static loopback** - drives TX dominant/recessive and verifies RX
   follows through the L9637D
2. **K byte stream** - transmits all 256 byte values (0x00-0xFF) at the
   10.4 kbaud K-line bit rate and checks each echoes back intact
3. **L-line toggle** - asserts the L pulldown FET and verifies the line
   follows: through L_RECV on boards that route it, or through the L_SENSE
   ADC input on v3.3+. Skipped where `CONFIG_APP_L_SEND_ENABLED` is off
   (see below), which is the default on every board before v3.3.

## Running the test

1. Enable in `local.conf`:
   ```
   CONFIG_APP_BOARD_L0DESTAR_V2_6_KLINE=y
   CONFIG_APP_KLINE_TEST=y
   ```

2. Build and flash:
   ```
   ./build.sh && ./flash.sh
   ```

3. Reset the board. Serial output shows:
   ```
   *** ISO-9141 TEST ***
   K1 static: idle=1 TX=0->RX=0 TX=1->RX=1 OK
   K1 loopback: TX=P0.0 RX=P0.1
   K1 loop: 256/256 bytes OK
   L-line: idle=1 send=1->0 send=0->1 OK
   PASS: ISO-9141 test
   *** ISO-9141 TEST DONE ***
   K-line test complete - halting.
   ```

4. Comment out `CONFIG_APP_KLINE_TEST=y` when done.

## Opening a session with a vehicle

`CONFIG_APP_KLINE_INIT_AT_BOOT=y` (in `local.conf`) makes the tracker try to
open a diagnostic session with the vehicle once at boot, report the result on
the console and as an alert once the modem is up (priority 1 if a session
opened, 0 if nothing answered), and then start as normal — including the
power-on FOTA check, so a bench build with a lower version than the fleet's
swaps itself out for the production image straight after reporting.  It
sends nothing over K beyond the init itself:

1. **5-baud init** (ISO 9141-2 and ISO 14230-4): address 0x33 at 5 baud on K,
   and on L where `CONFIG_APP_L_SEND_ENABLED` allows it, then wait for the
   0x55 sync byte and two key bytes and acknowledge them.
2. **Fast init** (ISO 14230-4 only), if the 5-baud init got no answer: a
   25 ms low / 25 ms high wake-up pulse followed by one StartCommunication
   request (`C1 33 F1 81 66`).  Most KWP2000 ECUs from about 2000 on,
   Toyota's included, only respond to this one.
3. **Physical-address scan**, if the functional address gets no reply either:
   a fast init to every target address 0x01-0xFE in turn, stopping at the
   first ECU that opens a session.  Pre-OBD-II-mandate JDM cars answer the
   maker's tester on their own ECU addresses and may ignore 0x33 entirely.
   About half a second per address, so up to two minutes.
4. **5-baud address scan**, if that finds nothing: the slow init to every
   address 0x01-0xFE in turn, for ECUs that only wake to their own address
   at 5 baud (VW's are the well-known case).  About three seconds per
   address, so up to thirteen minutes.

Serial output for a KWP2000 ECU that ignores the slow init:

```
*** K-LINE INIT ***
TX=P0.1 RX=P0.3
bus idle: RX=1, low for 0/300 ms
slow init: address 0x33 on K only
  no sync byte within 400 ms
fast init: 25 ms wake-up then StartCommunication C1 33 F1 81 66
  response after 31 ms: 83 F1 10 C1 E9 8F 1D
  ECU address 0x10, key bytes: KB1=0xE9 KB2=0x8F — ISO 14230-4 KWP2000
PASS: K-line communication established via fast init (ISO 14230-4 KWP2000)
*** K-LINE INIT DONE ***
```

Every bit the board drives is read back through the transceiver, so a
transmitter that is not reaching the wire shows up as an `echo:` line rather
than as a silent ECU.  The echo is of the transceiver's own bus pin, though,
which idles high off its internal pull-up: an open K wire looks the same as an
idle vehicle bus, so a clean run with no reply does not prove the wire reaches
pin 7 of the connector.

## The L line

Driving the L line is gated by `CONFIG_APP_L_SEND_ENABLED`, and it is **off
by default on every board before v3.3**. Those boards switch the L pulldown
FET (2N7002) straight across the wire: an L wire shorted to battery looks
exactly like a healthy idle one (both sit at 12-16 V), and asserting L_SEND
then saturates the FET into the short, where it dissipates 1-12 W in a SOT-23
and fails inside the first address bit of a 5-baud init - sometimes gate-first,
putting battery voltage on the L_SEND GPIO and taking the nRF9151 with it.
`../hardware/l0destar_v3.2/README.md` has the full write-up. With the gate off
the pin is still parked low (FET off) and `kline_l_send()` returns `-EPERM`, so
nothing in firmware can assert it; the cost is the L half of a 5-baud init.

v3.3 fixed the hardware - an AL5809-90 in series limits the pulldown to 90 mA
with thermal shutdown - and added **L_SENSE**, a tap on the wire through a
1N4148 (cathode to L) and a 47K. The diode blocks the vehicle's 12 V from ever
reaching the pin, so the line can only be read by sourcing current into it:
firmware samples it on the SAADC with the internal pull-up resistor ladder
engaged (~400K to VDD).

| L wire | Reading |
|--------|---------|
| pulled low (our FET, or an ECU) | diode conducts, ~0.7-0.9 V |
| high, open, or shorted to battery | diode reverse biased, runs to the 3.6 V full scale |

`CONFIG_APP_L_SENSE_LOW_MV` (default 1500) splits the two. A plain GPIO input
cannot: the nRF's ~13K internal pull-up against the 47K leaves even a grounded
line at ~2.7 V, above VIH. Zephyr's ADC driver hard-codes the ladder to bypass,
so `src/hw_kline.c` drives the SAADC through nrfx.

`kline_l_line_probe()` pulses the pulldown for 5 ms and reports whether the
line actually went low - a line that stays high is being held up by something
low-impedance, i.e. shorted to battery, and the init must not be attempted.

**Pin requirement:** the SAADC can only sample AIN0-AIN7, which are P0.13 to
P0.20 on the nRF9151. v3.3 puts L_SENSE on P0.14 (AIN1) and moves the
PP3V3_GPS rail sense, which only ever needed a digital read, to P0.05.
`kline_l_sense_init()` rejects any `CONFIG_APP_PIN_L_SENSE` outside that
range ("L_SENSE on P0.x has no SAADC channel") and the sense reports
unavailable.

## Troubleshooting

**K1 static FAIL (TX=0 -> RX=1)** - RX doesn't follow TX through the
L9637D. Check:
- K_EN domain is up (serial should show "K domain on")
- AUX domain is up (powers the TXS0104E VCCA)
- Correct board variant selected (`V2_6_KLINE`, not `V2_6_CAN`)
- L9637D is populated and has 12V on its Vs pin

**Byte mismatches** - bit-timing drift. The K-line bit rate is 10.4 kbaud
(96 us/bit), bit-banged with `k_busy_wait`. Check that no high-priority
interrupts are starving the bit-bang loop.

## Signal path (v2.6K)

```
nRF P0.0 (K1_TX) --> TXS0104E A2/B2 --> L9637D TxD --> K-line
                                                          |
nRF P0.1 (K1_RX) <-- TXS0104E A1/B1 <-- L9637D RxD <----+
```

Both AUX (TXS0104E VCCA) and K (L9637D Vs, TXS0104E VCCB) domains must
be powered for the signal path to work.
